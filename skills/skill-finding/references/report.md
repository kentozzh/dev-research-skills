# Skill choice report

Use current `report --format json` as the authority for formal order, eligibility and indices. The Markdown renderer supplies the evidence-linked baseline; make the final explanation specific to the user from recorded judgments. Default first choice is `formal[0]`. If a different conditional alternative fits a particular preference, name that condition; revise/reassess before changing formal order. With no formal result, surface any qualitative skill findings and the missing comparison facts. Keep unverified host installation explicit.

1. State the first choice, then current task/host, hard conditions, allowed adaptation, preferences and assumptions.
2. Compare formal results using repository + exact `SKILL.md` path/link, verified commit SHA or unresolved source ref, task fit, repository-level Star/Fork/Watch, license scope, host/dependency costs, maintenance basis, U/P/M and index. Show a condition × candidate matrix including important pending checks and exclusions. Only describe a skill as an alternative if its hosting repository has at least 10,000 verified stars. Never label repository counts as a skill's independent Star or usage.
3. Explain why the first choice leads and when an alternative fits better. State reusable workflow/templates/helpers separately from concrete adaptation: which tool/interface must change, which dependency/permission is needed, and what input/output contract must remain. Cite actual source observations, not just the numerical index. Show all U judgments and actual reading depth. Repository proxies do not establish a skill's last update.
4. Propose one minimal representative validation task: target host, sample input, expected output, tool/dependency mapping to inspect, and pass/fail observations. State it has not been executed. Do not install or invoke the skill as part of discovery.
5. Separate qualitative results, same-repository supplements and pending items, with missing facts/adaptation costs. A same-repository third skill may be useful despite the diversity cap; do not promote it into the formal five. A collection/tutorial remains discovery metadata, not a pending skill recommendation.
6. Explain exclusions by actual failed conditions. Missing license differs from evidenced incompatible terms. An unavailable mandatory host tool differs from a documented allowed replacement. An irrelevant skill can live inside a highly popular repository.
7. Report actual repository discoveries, concrete reads/attempts, assessed skills and group size, source observation times, verified path/SHA, run/revision/snapshot, live provider limits, host searches, truncated inventories, failed/missing reference reads and unresolved external/shared dependencies. Preserve scoring reference time separately from retrieval/generation time. Explain omitted items, closeness and preference sensitivity including unchanged outcomes. The index is an engineering heuristic, not a quality probability.

Evidence is linked next to the claim. Source facts, Agent judgments and proposed validation remain distinguishable. Return fewer than five if fewer qualify; do not fill slots with tutorials, duplicates, unsupported host-specific skills or license-unknown candidates.

Place clickable original links beside each recommendation and alternative. Use the frozen provenance.source_index for the complete candidate appendix, including eligible overflow, excluded, pending, and discovery-only entries. Preserve each link’s access status independently of the candidate’s disposition. Give each distinct skill its own repository and concrete SKILL.md links. Prefer observed commit-pinned files and cite shared dependencies at their verified scope.
