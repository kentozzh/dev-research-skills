# Tool choice report

Use the current structured `report --format json` as the numerical, eligibility and formal-order authority. The Markdown renderer supplies a reproducible baseline; the Agent makes the final explanation specific to the request using the recorded judgments and source documents.

State the purpose and use the first item in the formal list as the default first choice. Name the condition and evidence supporting any conditional alternative. Revise and reassess before presenting a changed formal order. When the formal list is empty, identify any qualitative architecture or component findings and the evidence still needed to rank them. Report no qualifying candidates only when the qualitative list is also empty.

For architecture reference, name the formal position under that contract and link each design claim to the source file or design section checked. Describe module boundaries, inputs, outputs, trade-offs and transfer conditions. Explain how deployment stack, archive status and maintenance affect the design's applicability. Distinguish the design observed in the repository from the adaptation proposed for the user's project. Propose a walk-through with a representative input and expected outputs at the relevant boundaries.

For component reuse, explain the candidate's documented interfaces, dependencies, environment fit, applicable license and integration costs. Propose a minimal interface task for the target environment with an input, expected output and acceptance criteria. Mark proposed validation as unexecuted in either case. If the same repository appears in both contracts, give each recommendation its own formal position and supporting reasons. Use the engine's order for each contract.

Preserve this order.

1. One-sentence first choice, or no confirmed eligible candidate.
2. Current hard conditions, preferences and explicit assumptions.
3. Show the formal positions, identity and links, requirement coverage, raw Star/Fork/Watch, maintenance and version signals, license observations, U/P/M and index in a table. Follow with a condition × candidate matrix. Include key excluded and pending alternatives with the evidence behind each judgment.
4. Explain why the first choice leads and when an alternative fits better, using evidence relevant to the current purpose. Report the usability judgments, reading depth, limits and maintenance basis. Include the proposed validation for this purpose.
5. Qualitative/supplementary and pending candidates, with specific missing facts or adaptation costs. Do not intermingle them with the ranked formal table or assign invented indices.
6. Key exclusions and failed conditions. Label archived candidates “历史/受限方案” for current development. Long-lived stable projects with no release remain separate from archived ones.
7. Data scope: actual discovery/deep-read/assessment/group counts, run revision/snapshot, provider and host-search limits, failed routes and actual source observation times; weights, omitted dimensions, closeness and sensitivity outcomes. Index is an engineering heuristic, not a quality probability. Include conditional first choices if sensitivity changes them; report unchanged outcomes too. Link the evidence next to claims. Scoring reference time and report generation time do not mean fresh retrieval.

An explicit Windows, offline or license requirement applies to either purpose. Keep required license checks pending when the evidence is missing. For architecture without an explicit license condition, an unknown license can be reported as an observation while the checked design informs the comparison. R4 can lead R3 even when the R3 index is higher. A stable project with no releases may qualify when the task's conditions are met.

Place clickable original links beside each recommendation and alternative. Use the frozen provenance.source_index for the complete candidate appendix, including eligible overflow, excluded, pending, and discovery-only entries. Preserve each link’s access status independently of the candidate’s disposition. For architecture decisions, cite the inspected module or design document directly and explain the transfer condition.
